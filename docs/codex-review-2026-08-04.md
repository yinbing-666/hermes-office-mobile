# Hermes Office Mobile APP Review

## 一、总体结论

当前项目已经具备一个可运行的移动端 AI 办公控制台雏形，主要能力包括：

- 多 Agent 状态查看与员工详情
- 任务、阻塞任务和 outbox 补投
- 选题、进化、Token 使用量和通道健康
- 工作空间与专家团派活
- 工作流画布编辑和模拟运行
- 本地登录、角色授权、CSRF、幂等和限流

**总体判断：基础设施和安全边界比普通 MVP 完整，但产品主线仍不够聚焦。**

现在更像：

> “Hermes 状态监控 + 多个实验功能集合”

还不像：

> “用户每天打开后，知道该处理什么、交给谁、结果在哪里的 AI 工作台”。

最需要优先解决的不是继续增加页面，而是：

1. 明确首页的核心任务入口；
2. 修复自动补投和工作流的真实交互缺陷；
3. 消除离线假数据造成的状态误判；
4. 将“发送、处理中、待确认、已完成”建立成统一的任务生命周期。

# 二、产品定位与信息架构

## 2.1 当前定位判断

### 做得好的地方

- “小黑 / 小橙 / 小金”角色有明确分工，产品记忆点较强。
- 办公室、员工、任务、空间、工作流等概念符合 AI 员工工作台方向。
- `frontend/src/App.tsx` 中已经有较完整的任务状态、投递状态和失败原因映射。
- `backend/main.py` 对真实发送、outbox、API Server 离线等状态区分比较诚实，没有直接把本地入队伪装成已送达。
- `ROADMAP.md` 已形成“真实性优先”“写操作需确认”“模拟态不得伪装真实完成”等判断标准，这对产品可信度很重要。

### 主要问题

当前导航包含 7 个一级入口：

- 办公室
- 空间
- 员工
- 选题
- 工作流
- 进化
- 动态

这些页面的职责边界不完全一致：

- “办公室”是总览页；
- “动态”是任务与 outbox 页；
- “空间”同时包含空间管理、单人派活、专家团和深度分析流水线；
- “员工”既是 Agent 详情，又包含发送任务；
- “工作流”是独立编辑器；
- “进化”更像系统资产审计；
- “选题”是一个业务垂直工具。

因此产品现在存在明显的**功能并列化**问题：每个页面都有功能，但用户不容易理解今天应该从哪里开始。

## 2.2 建议的信息架构

建议收敛成 4 个一级入口：

### 1. 首页 / 今日

只回答三个问题：

- 现在谁在线？
- 哪些任务需要我处理？
- 我下一步可以派什么活？

建议首页优先展示：

1. 阻塞任务；
2. 待确认操作；
3. 正在运行的任务；
4. 最近完成结果；
5. Agent 在线状态；
6. 快速派活入口。

当前 `OfficePage` 中的虚拟办公室、资源统计、通道健康、员工列表、最近任务等内容较多，应将低频诊断信息折叠到“系统状态”。

### 2. 任务

统一承载：

- 运行中
- 阻塞
- 待补投
- 已完成
- 失败
- 最近产出

当前“任务动态”已经接近核心页面，但还混入了专家团召集、outbox 自动补投等操作。建议拆出统一任务详情模型，所有任务都可进入同一种详情抽屉或详情页。

### 3. 员工

用于：

- Agent 状态
- 能力和角色
- 最近任务
- 派活
- 最近回复

不建议在首页和空间页重复渲染大量 Agent 操作。

### 4. 工作台

将当前“空间”和“工作流”整合为工作台下的两个模式：

- 协作空间：多人 Agent 协作
- 自动化工作流：节点式流程

“选题”和“进化”建议作为业务卡片或二级工具入口，而不是与首页、任务、员工并列。

## 2.3 当前信息过载位置

### `frontend/src/App.tsx:487`

`OfficePage` 同时承载：

- 虚拟办公室
- Agent 状态
- 任务概览
- Token 统计
- 通道健康
- PWA 安装提示
- 员工列表

这些模块都合理，但全部在首页展示，会削弱主任务优先级。

建议：

- 首页只保留“待处理任务 + Agent 状态 + 快速派活”；
- Token、通道健康、PWA 安装移动到“系统状态”折叠区；
- 虚拟办公室保留，但缩小成品牌化视觉入口，而不是占据主要工作空间。

### `frontend/src/App.tsx:1431`

`ActivityPage` 同时包含：

- 任务统计
- 阻塞任务
- 专家团
- outbox
- 自动补投
- 任务列表
- 任务详情

这已经成为第二个“超级页面”，建议将专家团放回“空间”，outbox 作为任务过滤项或系统状态，不要继续堆叠在任务页顶部。

# 三、前端代码质量

## 3.1 主要优点

- `WorkflowPage` 已通过 `lazy` 拆分，避免工作流编辑器直接阻塞主包。
- `frontend/src/api.ts` 有统一的 `getJson`、`postJson` 和安全错误映射。
- `frontend/src/types.ts` 已建立较完整的任务、Agent、outbox、进化数据类型。
- 发送操作使用幂等键，outbox 重试也有状态反馈。
- 多数异步请求有 loading、offline、error 等状态。
- 任务详情对敏感技术字段和异常原因做了显示层处理。

前端构建和 TypeScript 检查目前可以通过。

## 3.2 主要问题

### 1. `App.tsx` 过度膨胀

`frontend/src/App.tsx` 当前约 2129 行，混合了：

- 页面路由状态
- 认证状态
- API 调用
- Agent 元数据
- 任务格式化
- 首页组件
- 员工详情
- 空间页
- 任务页
- 选题页
- 进化页
- 活动页
- outbox 自动重试逻辑

这会导致：

- 修改一个页面容易影响全局状态；
- 状态依赖难以追踪；
- 页面级测试困难；
- 后续加入新 Agent 或新任务状态时风险升高。

建议拆分为：

```text
frontend/src/
  app/
    AppShell.tsx
    navigation.ts
    session.ts
  pages/
    OfficePage.tsx
    AgentPage.tsx
    TasksPage.tsx
    WorkspacePage.tsx
    TopicsPage.tsx
    EvolutionPage.tsx
  components/
    TaskCard.tsx
    TaskDetail.tsx
    AgentCard.tsx
    OutboxCard.tsx
    StatusPill.tsx
  domain/
    agents.ts
    tasks.ts
    workspaces.ts
```

### 2. 页面状态和业务状态混在一起

例如 `App` 同时维护：

- `offline`
- `loading`
- `authError`
- `retrying`
- `autoRetryEnabled`
- `autoRetryReport`
- `cameFromOffice`
- 多个页面的 selected 状态

建议至少抽出：

- `useSession()`
- `useOfficeData()`
- `useOutboxRetry()`
- `useUrlNavigation()`

### 3. `Workspace` 类型仅存在于前端

`Workspace`、`WorkspaceLog`、`WorkspaceActivityData` 在 `App.tsx` 中本地定义，后端没有形成同等稳定的契约。

这会使前后端逐渐出现：

- 字段名称不一致；
- 状态枚举不一致；
- 前端能存但后端不能理解；
- API 修改后只能靠手工联调发现问题。

建议将后端响应结构整理成明确的 API schema，并在前端建立对应类型，必要时生成 OpenAPI 类型。

### 4. API 错误和离线 fallback 语义混淆

`frontend/src/api.ts:149-165` 中，除 401/403 外，所有 GET 失败都会返回 mock 数据：

```ts
return { data: fallback, offline: true };
```

但 mock 数据中包含：

```ts
status: 'online'
port_listening: true
```

这与 `docs/acceptance.md` 和 `ROADMAP.md` 中“离线时不伪造在线、送达或完成状态”的标准不完全一致。

建议：

- 网络失败时只返回空数据和明确错误；
- 若必须展示演示数据，使用独立的 `demoMode`；
- 演示数据中的状态必须统一标记为 `demo` 或 `unknown`；
- 页面顶部显示“演示数据”，不能只显示“离线数据”。

### 5. 缺少前端测试与 lint

`frontend/package.json` 只有：

- `dev`
- `build`
- `preview`

没有：

- 单元测试
- 组件测试
- lint
- format
- e2e smoke test

当前后端有 41 条测试，但前端的关键风险主要集中在状态和交互，建议至少补：

- `api.ts` 错误映射测试；
- outbox 自动补投状态测试；
- URL 导航恢复测试；
- Workflow 节点和连线 reducer 测试；
- 390px 视口下的导航与溢出测试。

### 6. 依赖版本使用 `latest`

`frontend/package.json:8-21` 使用了：

```json
"@vitejs/plugin-react": "latest",
"react": "latest",
"react-dom": "latest",
"typescript": "latest",
"vite": "latest"
```

虽然 `package-lock.json` 能暂时锁定安装结果，但后续重新安装或更新 lockfile 时会引入不可预测变更。

建议：

- 使用明确版本；
- 通过 Renovate 或 Dependabot 定期升级；
- 在 CI 中固定 Node/npm 版本；
- 将构建环境版本写入 README 或 `.nvmrc`。

# 四、UI / UX Review

## 4.1 移动端优先

### 已做得不错

- `.app-shell` 将主内容限制在 480px，符合移动端窄屏布局。
- 底部导航预留了安全区域和底部空间。
- 390px 视口下长文本有截断和收敛处理。
- 工作流页面在 430px 以下切换为单列。
- 登录按钮、输入框等关键控件尺寸基本满足触控要求。

### 需要改进

#### 1. 底部导航承载过多一级功能

7 个 tab 在 390px 屏幕上会造成：

- 图标和文字过小；
- 入口认知成本高；
- 当前页面状态不够突出；
- 新增功能后继续压缩。

建议保留 4 个一级 tab：

```text
今日 / 任务 / 员工 / 工作台
```

其余入口放入工作台或设置页。

#### 2. 页面标题缺少上下文

顶部只显示当前 tab 标题，任务详情、Agent 详情、工作空间详情等路径主要依赖页面内部标题。建议在移动端加入：

- 返回按钮；
- 面包屑或上下文副标题；
- 当前工作空间 / Agent 名称。

#### 3. 失败状态与重试入口不够统一

不同页面有各自的错误文案和重试方式：

- topics 自己处理；
- outbox 自己处理；
- Agent 发送自己处理；
- 页面初始 GET 失败则统一 fallback。

建议建立统一的 `AsyncStateCard`：

```text
加载中
已连接
离线
失败
需要重新登录
无数据
```

所有页面使用同一套语义和视觉。

## 4.2 Marvis Office 风格一致性

### 符合的部分

- 米灰、白底、细边框；
- 线性图标；
- 轻量卡片；
- 颜色整体克制；
- 没有使用 emoji 作为主要交互元素。

### 不一致的部分

`frontend/src/styles.css` 中仍有较多：

- 阴影；
- 3D 办公室平台；
- 渐变；
- 彩色流程节点；
- 圆角胶囊标签；
- 选题页额外的蓝/红色视觉体系。

尤其是 `VirtualOfficeCard` 的 3D 场景与 Marvis Office 的“浅色办公、克制线性界面”存在一定风格偏差。它更像品牌展示插画，而不是办公工作台本身。

建议：

- 保留虚拟办公室作为首页品牌区域；
- 减少 `box-shadow` 和立体层；
- 把 3D 场景高度压缩；
- 将任务、状态和结果卡片作为主要视觉焦点；
- 统一选题页和流水线页的颜色变量，避免页面之间像不同产品。

## 4.3 交互路径

### 当前核心路径

```text
首页 → 员工 → 输入任务 → 发送
首页 → 任务动态 → 查看阻塞 → 找 Agent
空间 → 召集专家团 → 查看投递结果
工作流 → 编辑节点 → 模拟运行
```

这些路径可以运行，但没有形成完整闭环：

```text
提出目标 → 派给 Agent → 处理中 → 需要确认/阻塞 → 结果交付 → 继续派发
```

尤其缺少：

- 结果归档；
- 结果与任务的关联；
- 任务完成后的下一步；
- 用户确认节点；
- Agent 回复历史；
- 搜索和筛选跨页面联动。

建议所有成功发送都生成统一任务记录，并让用户在任务详情中继续查看结果，而不是只显示一次 `response_preview`。

# 五、工作流工作室 Review

## 5.1 MVP 是否有价值

**有价值，但目前更接近“流程编辑器原型”，还不是可用的工作流产品。**

作为 MVP，它已经具备：

- 节点调色板；
- 节点拖拽；
- 属性编辑；
- 节点删除；
- 连线显示；
- localStorage 草稿；
- 导入、导出、清空；
- 模拟运行日志；
- 明确的模拟模式文案。

这足以作为作品集中的交互原型，能够展示产品方向和前端实现能力。

但它目前没有形成真实的业务价值，因为：

- 节点关系没有决定执行顺序；
- 连接目标不是真正的用户选择；
- 保存主要依赖浏览器 localStorage；
- 后端工作流保存接口没有接入；
- 执行始终是模拟；
- 节点配置字段没有真正约束；
- 没有运行历史、版本、失败恢复和结果输出。

## 5.2 关键工作流问题

### High：连线没有连接到用户实际选择的目标

`frontend/src/WorkflowPage.tsx:282-291` 中，指针抬起时直接选择：

```ts
const target = nodes.find((node) => node.id !== connectFromId);
```

这意味着从一个节点拖出连线后，并不是连接到用户松手的位置，而是连接到列表中第一个其他节点。

实际表现可能是：

- 连线目标错误；
- 用户无法稳定创建复杂流程；
- 画布显示与用户意图不一致。

建议：

- 通过 pointer 坐标命中目标节点或输入端口；
- 只允许连接到实际命中的 input port；
- 拒绝自连接和重复边；
- 对非法连接显示原因。

### High：模拟运行忽略 edges

`frontend/src/WorkflowPage.tsx:181-220` 按 `y/x` 坐标排序节点：

```ts
const sortedNodes = [...nodes].sort((left, right) => left.y - right.y || left.x - right.x);
```

这与用户画出的图结构无关。移动节点位置后，执行顺序就可能改变；即使连线完全不同，模拟结果也一样。

建议：

- 从 start 节点开始；
- 按 edges 构建邻接表；
- 拓扑遍历；
- 检查环路、孤立节点、缺少 start/end；
- 在日志中展示真实的节点路径。

### Medium：工作流保存没有接入后端

画布 footer 标注为：

```text
localStorage 草稿
```

而后端已经有：

- `GET /api/workflows`
- `POST /api/workflows`

但 `WorkflowPage` 没有调用这些接口。

结果是：

- 换设备无法访问工作流；
- 清理浏览器数据后草稿丢失；
- 多用户或多会话没有隔离；
- 工作流无法形成服务器端版本和审计。

建议 MVP 下一步先接入：

- 工作流列表；
- 保存当前版本；
- 最近更新时间；
- 基础版本号；
- 保存失败提示；
- localStorage 作为离线缓存而不是唯一存储。

### Medium：节点类型虽多，但能力不真实

当前节点包括：

- LLM
- 工具调用
- 微信 Gateway
- 条件分支
- Hermes 调用

但多数只展示节点，不具备真实配置和验证。建议第一版只支持一个诚实、可验证的子集：

```text
start → hermes_call → end
```

其他节点暂时标记为“规划中”，避免用户误以为已经具备执行能力。

# 六、风险与 Bug 分级

## Critical

当前没有发现可以明确判定为立即导致数据泄露或大范围破坏的 Critical 问题。

不过公网写接口仍属于高风险能力，必须继续保持严格的运行态核验，不能只依据源代码判断安全已经生效。

## High

### H-01：自动补投开关无法真正开启

文件：`frontend/src/App.tsx:1962-1978`

在没有旧消息时，代码只设置了：

```ts
setAutoRetryReport(...)
```

在正常可自动补投的路径中，没有调用：

```ts
setAutoRetryEnabled(true)
```

因此用户点击“自动补投”后，界面仍不会进入运行状态，60 秒定时器也不会启动。

影响：

- 核心 outbox 能力表面存在、实际不可用；
- 用户可能以为系统会自动恢复投递；
- 任务恢复链路被静默中断。

建议：

- 在通过 stale 检查后显式开启开关；
- 开启后立即执行一次还是等待 60 秒，需要在产品上明确；
- 加 UI 测试覆盖“开启 → 定时执行 → 关闭”。

### H-02：工作流连线目标错误，模拟顺序不由连线决定

文件：`frontend/src/WorkflowPage.tsx:181-220、282-291`

这是工作流编辑器的核心语义错误，具体见上一节。

影响：

- 复杂流程无法可靠编辑；
- 用户画出的流程与执行日志不一致；
- 作品集演示时容易被直接发现。

### H-03：离线 fallback 会展示“在线”假数据

文件：`frontend/src/api.ts:3-26、149-185`

GET 请求失败后使用 mock 数据，而 `mockAgents` 包含在线状态。页面只显示“离线数据”，但卡片仍可能显示“小黑在线”“端口可连接”等信息。

影响：

- 用户误判 Agent 状态；
- 可能在错误的在线判断下进行发送或重试；
- 与项目自身“真实性优先”原则冲突。

建议改为：

- 离线状态只展示 `unknown`；
- 禁用依赖真实状态的操作；
- mock 数据单独进入 demo 模式；
- 失败响应保留错误原因，不要全部降级为正常业务数据。

### H-04：专家流水线在 async endpoint 内执行同步阻塞操作

文件：`backend/main.py:2065-2171`

`run_expert_pipeline` 是 `async def`，但内部直接调用同步的：

- `_send_to_hermes`
- `_wait_for_response`
- 多次串行等待

每个 Agent 最长可能等待约 40 秒，后续还有综合请求。

影响：

- 一个流水线请求可能长期占用 FastAPI 事件循环；
- 同一 BFF 的健康检查和其他请求延迟升高；
- 移动端容易长时间显示“正在召集”。

建议：

- 将同步 Hermes 调用放入线程池；
- 更好的方案是拆为后台任务 / job；
- API 立即返回 `batch_id`；
- 前端轮询或 SSE 获取步骤状态；
- 为单个 Agent、整条流水线和最终综合分别设置超时。

### H-05：认证默认值仍是 disabled，存在部署配置失效风险

文件：`backend/local_security.py:187-209`

代码默认：

```python
HERMES_AUTH_MODE=disabled
```

虽然 `backend/systemd/hermes-office-mobile-bff.service.d/auth.conf` 设置了 `local`，但如果通过 README 中的手动 uvicorn 命令启动，或 systemd drop-in 未加载，服务会退回关闭认证状态。

影响：

- 运维启动方式不同可能得到不同的安全边界；
- 源码默认行为与公网产品要求不一致；
- 仅凭构建通过无法证明线上写接口受保护。

建议：

- 生产启动脚本强制设置 `HERMES_AUTH_MODE=local`；
- 在非 localhost 绑定时拒绝 `disabled`；
- `/api/health` 返回脱敏的 auth mode；
- 部署检查明确校验 systemd 环境和公网拒绝证据。

# 七、工作流工作室下一步优先级

建议不要立即继续增加节点类型，而是按以下顺序补齐：

## P0：正确编辑
